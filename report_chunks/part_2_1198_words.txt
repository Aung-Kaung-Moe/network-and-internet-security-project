It demonstrates that a honeypot is more useful when it records specific context, such as the username, attempted path, selected bait file, token role, source address, and recommended response. CHAPTER 2 LITERATURE REVIEW 2.1 Honeypot Concepts Honeypots are commonly classified by purpose and interaction level. A production honeypot supports operational detection, while a research honeypot is designed to collect information about techniques and behavior. Low interaction systems emulate a narrow set of services and reduce risk, whereas high interaction systems provide a fuller environment at the cost of greater containment and maintenance requirements [3], [4]. The present project is a low to medium interaction application honeypot. It offers real HTTP behavior and stateful sessions but does not provide an attacker with an operating system shell. Deception changes the meaning of an event. A failed login may come from an ordinary mistake, but opening a hidden decoy administration page or downloading fabricated borrower credentials has no normal business purpose. This makes bait interaction suitable as a high confidence detection signal. NIST guidance treats honeypots as a complementary detection technology rather than a replacement for ordinary controls [5]. The project follows that principle by combining the decoy with authentication checks, parameterized database queries, application logging, and Wazuh monitoring. 2.2 JSON Web Token Security RFC 7519 defines JWT as a compact representation of claims that may be signed or encrypted [1]. In this project the token contains a subject identifier, username, role, issue time, and expiration time. HS256 calculates a message authentication code over the encoded header and payload. If the key remains secret and has adequate entropy, a modified payload will fail verification. Two JWT weaknesses are relevant to the design. The first is acceptance of the none algorithm, which removes signature protection. The backend explicitly requires HS256, so this attack is rejected. The second is a weak HMAC key. RFC 8725 and the OWASP JWT guidance both state that human memorable or short secrets are vulnerable to offline guessing and recommend cryptographically generated keys of sufficient length [2], [6]. The project intentionally violates the key strength recommendation to create the learning scenario, while preserving algorithm verification so that students can observe the difference. 2.3 Web Application Threats The rule set reflects common web testing activities. OWASP identifies broken access control as a major risk because it can allow a user to act outside intended permissions [7]. IDOR is one form of this problem: an attacker changes an object identifier and tries to access another user's record [8]. SQL injection occurs when untrusted input changes the structure of a database query [9]. Automated password attacks and weak or default credentials are also recognized authentication failures [10]. The application does not deliberately make its SQLite statements injectable. It uses parameterized queries, then separately inspects login and API values for recognizable SQL injection probes. This separation is important. A detection exercise should observe malicious input without needing to let that input execute against the database. 2.4 Security Monitoring and Active Response Wazuh collects endpoint and application events through agents. Its localfile configuration can read a single line JSON log and forward each record for decoding and rule evaluation [11]. Custom rules allow local fields and event types to be assigned project specific rule identifiers and severity levels [12]. The indexer stores resulting alerts, and the dashboard provides search and visualization. Active response links a rule to a command that runs on a manager or agent [13]. Automation reduces response time, but it can also amplify a false positive. The project therefore associates the banning command only with rule 100500. Other detections remain visible to the analyst without changing the user's account. 2.5 Comparison of Approaches Approach | Strength | Limitation | Use in this project Ordinary application logging | Simple and low cost | Events may lack security context | Used for internal security_events records Network scanner or IDS | Observes traffic patterns | May not know user or application state | Represented by scanner and path probe detections Application honeypot | High signal from decoy interaction | Can be recognized if the decoy is unrealistic | Fake library administration page and CSV bait SIEM with custom rules | Central search and severity classification | Requires agent and rule configuration | Wazuh rules 100500 through 100507 Automated response | Fast containment | False positives can disrupt valid users | Restricted to forged admin bait downloads Table 2.1 Comparison of security monitoring approaches 2.6 Relevant Standards and Guidance The security design draws on several established sources. RFC 7519 and RFC 8725 define JWT behavior and secure implementation practices [1], [2]. The OWASP Top 10 and Web Security Testing Guide provide categories and testing methods for access control, authentication, injection, and object references [7]-[10]. NIST SP 800-115 supports planned technical security testing and emphasizes documenting methods, findings, and mitigation [14]. Wazuh documentation supplies the operational requirements for log collection, custom rules, and active response [11]-[13]. 2.7 Research Gap Many honeypot examples focus on network services such as SSH or on generic web decoys. Many JWT demonstrations stop after showing that a role claim can be forged. This project joins those topics into one traceable workflow: a realistic member account is compromised at the token level, the suspicious session is redirected rather than granted genuine administration access, bait interaction is converted into a structured SIEM alert, and a selected event can trigger an account response. The result is small enough for a student laboratory but broad enough to demonstrate detection engineering decisions.

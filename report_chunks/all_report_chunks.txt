ABSTRACT This project develops a web based library honeypot that combines an ordinary borrowing service with a controlled decoy administration area. The real application runs on localhost port 3000 and supports book browsing, registration, login, borrowing, return processing, overdue fines, and personal loan records. Authentication uses a signed JSON Web Token stored in the library_jwt cookie. For the purpose of the security exercise, the HS256 signing secret is intentionally weak, while unsecured tokens using the none algorithm are rejected. A user who recovers the secret and changes the token role from user to admin is diverted to a fake administration page on port 4000. The page contains believable borrower credential, loan, and fine files. Access to these files produces structured JSON security events. A Windows Wazuh agent monitors the JSONL event file and sends new records to a Docker based Wazuh manager, where custom rules classify eight types of suspicious activity. The highest severity rule can call an active response script that bans the attacking account and revokes its stored credentials. The completed prototype demonstrates how a deliberate vulnerability can be contained inside a local teaching environment and connected to monitoring, investigation, and response. It also shows the limits of this design: the weak key and decoy credentials are suitable only for an isolated laboratory and must never be carried into a production system. JSON Web Token, or JWT, is a compact format for carrying claims such as a user identifier and role [1]. A signed token can protect those claims from modification, but that protection depends on correct algorithm validation and a signing key with enough entropy. RFC 8725 specifically warns that weak symmetric keys can be recovered through offline dictionary or brute force attacks after an attacker obtains a token [2]. This weakness is useful in a controlled security exercise because it creates a clear path from an ordinary user account to attempted privilege escalation. The project deliberately uses the short key book for HS256 signing. It still rejects the none algorithm, so the exercise distinguishes an implementation that performs signature verification from one that uses an unsafe key. Once an altered role claim is accepted, the application does not expose real administrative data. Instead, it moves the suspicious session into a decoy service where later actions can be observed. Honeypots are systems or resources designed to attract activity that has little or no legitimate reason to occur. Their value comes from the high signal of an interaction and the opportunity to record attacker behavior [3], [4]. In this project the decoy is application specific. It looks like a library administration page and offers files that an attacker may consider valuable, while the files contain synthetic records. Wazuh then provides centralized rule matching, alert storage, dashboard investigation, and active response. 1.2 Problem Statement A normal library application can record failed logins, but a basic log entry does not show how several suspicious actions relate to one session. The project therefore addresses three connected problems. First, it needs a believable application in which normal users can perform real work. Second, it needs a contained attack path that demonstrates JWT role manipulation without exposing genuine administrator information. Third, it needs a monitoring pipeline that turns application events into searchable alerts and can respond automatically to a high confidence deception event. The design must also control false positives. A forgotten password should not automatically ban a member, and a scanner signature by itself may not prove compromise. For that reason, most custom rules are review only. Automatic account banning is reserved for the stronger signal produced when a forged administrator session downloads a bait file. 1.3 Project Objectives The main objective is to design and implement a local web honeypot that detects JWT role manipulation and records subsequent attacker activity. The specific objectives are: Build a usable library website with public book browsing, registration, login, borrowing, returns, due dates, and overdue fine calculation. Use an HS256 JWT cookie for authentication and deliberately configure a weak signing key for an authorized laboratory exercise. Reject unsecured JWTs using the none algorithm while allowing the weak secret to demonstrate a different JWT failure mode. Redirect forged administrator sessions from the real website on port 3000 to a fake administration page on port 4000. Generate structured security events for bait downloads, login brute force, decoy login, IDOR probes, SQL injection probes, scanner user agents, and path enumeration. Integrate the application with a Windows Wazuh agent and Docker based Wazuh server components. Use a custom active response for the high confidence bait download event while leaving lower confidence events for analyst review. 1.4 Project Scope The project is a single host laboratory deployment. The real and decoy web services run on Windows, while the Wazuh manager, indexer, and dashboard run in Docker containers on the same machine. SQLite stores application data locally. Testing is limited to accounts, traffic, and files created for this project. The system is not exposed to the public Internet and does not collect data from unrelated users. The scope includes detection and response demonstrations rather than enterprise hardening. It does not include TLS termination, multi factor authentication, a production password recovery process, distributed deployment, long term

CHAPTER 2 LITERATURE REVIEW 2.1 Honeypot Concepts Honeypots are commonly classified by purpose and interaction level. A production honeypot supports operational detection, while a research honeypot is designed to collect information about techniques and behavior. Low interaction systems emulate a narrow set of services and reduce risk, whereas high interaction systems provide a fuller environment at the cost of greater containment and maintenance requirements [3], [4]. The present project is a low to medium interaction application honeypot. It offers real HTTP behavior and stateful sessions but does not provide an attacker with an operating system shell. Deception changes the meaning of an event. A failed login may come from an ordinary mistake, but opening a hidden decoy administration page or downloading fabricated borrower credentials has no normal business purpose. This makes bait interaction suitable as a high confidence detection signal. NIST guidance treats honeypots as a complementary detection technology rather than a replacement for ordinary controls [5]. The project follows that principle by combining the decoy with authentication checks, parameterized database queries, application logging, and Wazuh monitoring. 2.2 JSON Web Token Security RFC 7519 defines JWT as a compact representation of claims that may be signed or encrypted [1]. In this project the token contains a subject identifier, username, role, issue time, and expiration time. HS256 calculates a message authentication code over the encoded header and payload. If the key remains secret and has adequate entropy, a modified payload will fail verification. Two JWT weaknesses are relevant to the design. The first is acceptance of the none algorithm, which removes signature protection. The backend explicitly requires HS256, so this attack is rejected. The second is a weak HMAC key. RFC 8725 and the OWASP JWT guidance both state that human memorable or short secrets are vulnerable to offline guessing and recommend cryptographically generated keys of sufficient length [2], [6]. The project intentionally violates the key strength recommendation to create the learning scenario, while preserving algorithm verification so that students can observe the difference. 2.3 Web Application Threats The rule set reflects common web testing activities. OWASP identifies broken access control as a major risk because it can allow a user to act outside intended permissions [7]. IDOR is one form of this problem: an attacker changes an object identifier and tries to access another user's record [8]. SQL injection occurs when untrusted input changes the structure of a database query [9]. Automated password attacks and weak or default credentials are also recognized authentication failures [10]. The application does not deliberately make its SQLite statements injectable. It uses parameterized queries, then separately inspects login and API values for recognizable SQL injection probes. This separation is important. A detection exercise should observe malicious input without needing to let that input execute against the database. 2.4 Security Monitoring and Active Response Wazuh collects endpoint and application events through agents. Its localfile configuration can read a single line JSON log and forward each record for decoding and rule evaluation [11]. Custom rules allow local fields and event types to be assigned project specific rule identifiers and severity levels [12]. The indexer stores resulting alerts, and the dashboard provides search and visualization. Active response links a rule to a command that runs on a manager or agent [13]. Automation reduces response time, but it can also amplify a false positive. The project therefore associates the banning command only with rule 100500. Other detections remain visible to the analyst without changing the user's account. 2.5 Comparison of Approaches Approach | Strength | Limitation | Use in this project Ordinary application logging | Simple and low cost | Events may lack security context | Used for internal security_events records Network scanner or IDS | Observes traffic patterns | May not know user or application state | Represented by scanner and path probe detections Application honeypot | High signal from decoy interaction | Can be recognized if the decoy is unrealistic | Fake library administration page and CSV bait SIEM with custom rules | Central search and severity classification | Requires agent and rule configuration | Wazuh rules 100500 through 100507 Automated response | Fast containment | False positives can disrupt valid users | Restricted to forged admin bait downloads Table 2.1 Comparison of security monitoring approaches 2.6 Relevant Standards and Guidance The security design draws on several established sources. RFC 7519 and RFC 8725 define JWT behavior and secure implementation practices [1], [2]. The OWASP Top 10 and Web Security Testing Guide provide categories and testing methods for access control, authentication, injection, and object references [7]-[10]. NIST SP 800-115 supports planned technical security testing and emphasizes documenting methods, findings, and mitigation [14]. Wazuh documentation supplies the operational requirements for log collection, custom rules, and active response [11]-[13]. 2.7 Research Gap Many honeypot examples focus on network services such as SSH or on generic web decoys. Many JWT demonstrations stop after showing that a role claim can be forged. This project joins those topics into one traceable workflow: a realistic member account is compromised at the token level, the suspicious session is redirected rather than granted genuine administration access, bait interaction is converted into a structured SIEM alert, and a selected event can trigger an account response. The result is small enough for a student laboratory but broad enough to demonstrate detection engineering decisions. CHAPTER 4 SYSTEM ARCHITECTURE AND IMPLEMENTATION 4.1 Overall Architecture Figure 4.1 Overall system architecture The browser first communicates with the real library service on port 3000. The Python backend serves the static HTML, CSS, and JavaScript files and exposes JSON API routes. It reads and updates the SQLite database in the same process. If a verified token contains an administrator role while the associated database account remains an ordinary user, the request is treated as a role manipulation signal and is redirected to the decoy service on port 4000. Security events are written to logs/wazuh-honeypot-alerts.jsonl. The Windows Wazuh agent monitors this file and sends new entries over TCP to the Wazuh manager container. The manager decodes the JSON and evaluates local rules. Matching alerts are stored by the indexer and displayed in the dashboard. For rule 100500, the manager can instruct the reporting Windows agent to run the ban script. 4.2 Attack and Deception Flow Figure 4.2 Intended JWT manipulation and honeypot flow The intended exercise begins with a valid member login. Because JWT payloads are encoded rather than encrypted, the role claim can be inspected. The attacker performs an offline dictionary search against the HS256 signature and discovers the deliberately weak key. After changing the role to admin and re-signing the token, the attacker replaces the library_jwt cookie. A request to the real site webadmin path is then redirected to the fake administration page. The decoy looks useful but does not expose a real administrator function. 4.3 Application Data Flow Registration inserts a user record with a generated identifier, the user role, and a derived password hash. Login compares the submitted value with the stored hash and issues a signed cookie after success. Borrowing creates a loan record, reduces copies_available, and calculates a due date fourteen days after the transaction. A normal return closes the loan and increases book availability. If the due date has passed, the interface displays 500 MMK for each overdue day and the return action is refused until the fine condition is addressed. The backend keeps operational and security data separate. Users, books, loans, tickets, bans, failed login attempts, and path probes are stored in SQLite. Events intended for Wazuh are appended to a JSONL file so the agent can consume them incrementally. SQLite is suitable for this local prototype because it is an in process, serverless database stored in a single file and requires no separate database service [15]. 4.4 Database Design Table | Purpose | Important fields users | Member identity and local role | id, username, full_name, role, password_hash books

The command passes the alert to backend/ban_account.py. The script extracts account_to_ban, inserts or updates the banned_accounts record, replaces the stored password hash with a revoked value, and removes the decoy password. Future login and token checks reject the account. Wazuh supports this model by allowing rules_id to select the alert that activates a command [13]. The webadmin decoy account is deliberately excluded from automatic banning. Its purpose is to let an analyst observe use of the planted credentials. A download by that account creates rule 100503 for review. This distinction prevents the shared decoy identity from being destroyed during every demonstration. 4.9 Environment Setup 1. The design keeps the deliberate weakness narrow: a short JWT secret and known decoy credentials. It does not depend on SQL injection, IDOR, or algorithm none being exploitable. Those behaviors are observed and reported while ordinary authorization and parameterized SQL remain in place. For that reason it receives level 12 and is connected to the account response. The webadmin account uses a similar page but a different event type, allowing the analyst to observe use of planted credentials without repeatedly disabling the shared decoy account. The login threshold was increased from five to ten failures in sixty seconds to reduce noise from ordinary password mistakes. The threshold is based on source IP rather than username. This is easy to explain and demonstrate, but it can combine several users behind one network address. Path brute force uses a lower threshold of three unknown paths in sixty seconds because normal navigation should remain inside the known route set. Scanner User Agent detection has lower confidence because headers can be changed or spoofed. SQL injection detection looks for quotes, backslashes, tautologies, comments, SQL keywords, union select patterns, delay functions, and schema names. These patterns provide visible evidence during a demonstration but are not a complete web application firewall. IDOR detection is more contextual because it compares the requested loan object with the authenticated user and records the actual owner when access is denied. 5.5 Results and Discussion The project achieved its main objective. A forged role does not reveal a genuine administrator dashboard; it leads to an instrumented decoy. The monitoring path preserves useful context from the application through the JSONL record and into Wazuh. Rule IDs make each demonstration easy to isolate in the dashboard, and the high confidence event can produce a visible change in SQLite through the banned_accounts table. The design also exposes an important operational lesson. Detection and response are different decisions. A suspicious User Agent, unknown path, or failed password sequence should alert an analyst, but these signals are not always reliable enough for automatic punishment. Bait download is narrower and therefore supports stronger automation. This distinction reduces the chance that a normal member is banned because of a typo or unusual browser behavior. 5.6 Challenges Encountered The real application and honeypot share the localhost name, so cookie scope and redirect behavior had to be designed carefully to avoid redirect loops. A query parameter used during early handoff testing made the decoy URL look suspicious. The final flow stores the short lived ticket in a cookie and leaves the visible URL at webadmin. Windows port reservations prevented Docker from binding the default Wazuh ports. Host ports were remapped while the manager retained its internal service ports. Custom rules initially matched only the parent JSON rule. Copying the updated local_rules.xml into the manager and validating the configuration corrected the issue. Active response required coordination between manager configuration and a script located on the Windows agent. Testing the script separately helped separate application, agent, and manager problems. Frequent Windows audit events made demonstrations noisy. Dashboard filters by custom rule range, rule group, or honeypot_program were used instead of deleting useful endpoint logs. 5.7 Lessons Learned The project showed that security monitoring works best when the application supplies meaningful context. A generic 404 or failed login count says less than an event that includes the attempted route, credentials, account, token role, and recommended action. It also showed that a deliberate vulnerability must be documented and contained. The weak signing key is useful only because the system is local, the admin data is fake, and the response path is visible. A second lesson is that configuration belongs to the system design. The Python code alone cannot produce a Wazuh dashboard alert. The agent localfile entry, TCP connection, manager rule file, indexer, dashboard, and active response configuration all have to agree. Testing each stage independently made troubleshooting more reliable. CHAPTER 6 CONCLUSION 6.1 Project Summary This project implemented a library management website and an application specific honeypot on one Windows host. Normal members use port 3000 to browse, borrow, return, and review books. A deliberately weak JWT signing secret supports an authorized role manipulation exercise. Suspicious administrator sessions are redirected to a decoy page on port 4000, where fake borrower files create high value detection events. A Windows Wazuh agent forwards those events to Docker based Wazuh services for rule matching, storage, investigation, and selected response. 6.2 Key Contributions A complete normal user workflow that makes the decoy part of a believable application rather than an isolated page. A contained JWT attack path that rejects algorithm none but demonstrates the risk of a weak symmetric signing key. A separate fake administration service with synthetic credential, loan, and fine files. Eight project specific Wazuh rules covering deception, authentication, access control, injection, scanning, and enumeration events. A selective active response that bans a forged personal account and revokes its stored credentials after bait interaction. A reproducible local architecture suitable for classroom demonstration and security analysis. 6.3 Project Limitations The prototype is intentionally not production ready. It uses HTTP on localhost, a weak JWT secret, known decoy credentials, and a simple password derivation scheme. Event thresholds are stored and calculated by a single Python process and are grouped mainly by source IP. The decoy may be recognized by a skilled attacker, especially if they compare service fingerprints or inspect the local environment. The system has not been load tested, independently penetration tested, or evaluated against public Internet traffic. Automatic banning changes an application account rather than blocking a network source. 6.4 Future Enhancements Move secrets and secure deployment values into environment configuration, and use a cryptographically random key outside the training mode. Replace the demonstration password derivation with a standard adaptive password hashing library such as Argon2id or bcrypt. Add TLS through a local reverse proxy and test secure, HttpOnly, and SameSite cookie behavior. Introduce correlation rules that combine scanner, path, login, and decoy events over a longer period without storing attempted passwords in clear text. Add a controlled fine payment workflow so overdue loans can be resolved without manual database changes. Use container volumes or deployment automation so custom Wazuh rules persist whenever manager containers are recreated. Evaluate decoy realism, false positives, detection latency, and resource use with a documented repeatable test set.

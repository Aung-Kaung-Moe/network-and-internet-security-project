The application writes login_bruteforce_detected only when the tenth failed login from the same source IP enters the previous sixty second window. It writes path_bruteforce when the third unknown route from the same IP enters its sixty second window. Wazuh then classifies the resulting event. This design keeps request context close to the application and keeps the XML rules simple. 4.8 Active Response and Account Revocation The active response configuration associates rule 100500 with ban-library-account.cmd at the local location, which means the command runs on the Windows agent that reported the event. The command passes the alert to backend/ban_account.py. The script extracts account_to_ban, inserts or updates the banned_accounts record, replaces the stored password hash with a revoked value, and removes the decoy password. Future login and token checks reject the account. Wazuh supports this model by allowing rules_id to select the alert that activates a command [13]. The webadmin decoy account is deliberately excluded from automatic banning. Its purpose is to let an analyst observe use of the planted credentials. A download by that account creates rule 100503 for review. This distinction prevents the shared decoy identity from being destroyed during every demonstration. 4.9 Environment Setup 1. Start the Docker Desktop service and run docker-compose up -d in the Wazuh single-node folder. The manager, indexer, and dashboard containers should become healthy. 2. Configure the Windows Wazuh agent to connect to the manager through the mapped TCP port and add the JSON localfile entry for wazuh-honeypot-alerts.jsonl. 3. Copy local_rules.xml to /var/ossec/etc/rules/local_rules.xml inside the manager, validate the configuration, and restart the manager container. 4. Copy ban-library-account.cmd to the Windows agent active-response bin folder and add the command and active-response blocks to the manager configuration. 5. Start WazuhSvc on Windows. Confirm that the agent appears active in the dashboard. 6. Run npm start in the project folder. This executes python backend/run_servers.py and starts ports 3000 and 4000. 7. Open the real library at http://localhost:3000 and the Wazuh dashboard at https://localhost. Use dashboard filters such as rule.id:100500 for testing. 4.10 Implementation Summary The completed implementation separates ordinary library work from the decoy service, records both operational and security state, and sends stable JSON events into Wazuh. The design keeps the deliberate weakness narrow: a short JWT secret and known decoy credentials. It does not depend on SQL injection, IDOR, or algorithm none being exploitable. Those behaviors are observed and reported while ordinary authorization and parameterized SQL remain in place.

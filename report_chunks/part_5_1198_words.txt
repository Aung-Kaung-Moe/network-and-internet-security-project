For that reason it receives level 12 and is connected to the account response. The webadmin account uses a similar page but a different event type, allowing the analyst to observe use of planted credentials without repeatedly disabling the shared decoy account. The login threshold was increased from five to ten failures in sixty seconds to reduce noise from ordinary password mistakes. The threshold is based on source IP rather than username. This is easy to explain and demonstrate, but it can combine several users behind one network address. Path brute force uses a lower threshold of three unknown paths in sixty seconds because normal navigation should remain inside the known route set. Scanner User Agent detection has lower confidence because headers can be changed or spoofed. SQL injection detection looks for quotes, backslashes, tautologies, comments, SQL keywords, union select patterns, delay functions, and schema names. These patterns provide visible evidence during a demonstration but are not a complete web application firewall. IDOR detection is more contextual because it compares the requested loan object with the authenticated user and records the actual owner when access is denied. 5.5 Results and Discussion The project achieved its main objective. A forged role does not reveal a genuine administrator dashboard; it leads to an instrumented decoy. The monitoring path preserves useful context from the application through the JSONL record and into Wazuh. Rule IDs make each demonstration easy to isolate in the dashboard, and the high confidence event can produce a visible change in SQLite through the banned_accounts table. The design also exposes an important operational lesson. Detection and response are different decisions. A suspicious User Agent, unknown path, or failed password sequence should alert an analyst, but these signals are not always reliable enough for automatic punishment. Bait download is narrower and therefore supports stronger automation. This distinction reduces the chance that a normal member is banned because of a typo or unusual browser behavior. 5.6 Challenges Encountered The real application and honeypot share the localhost name, so cookie scope and redirect behavior had to be designed carefully to avoid redirect loops. A query parameter used during early handoff testing made the decoy URL look suspicious. The final flow stores the short lived ticket in a cookie and leaves the visible URL at webadmin. Windows port reservations prevented Docker from binding the default Wazuh ports. Host ports were remapped while the manager retained its internal service ports. Custom rules initially matched only the parent JSON rule. Copying the updated local_rules.xml into the manager and validating the configuration corrected the issue. Active response required coordination between manager configuration and a script located on the Windows agent. Testing the script separately helped separate application, agent, and manager problems. Frequent Windows audit events made demonstrations noisy. Dashboard filters by custom rule range, rule group, or honeypot_program were used instead of deleting useful endpoint logs. 5.7 Lessons Learned The project showed that security monitoring works best when the application supplies meaningful context. A generic 404 or failed login count says less than an event that includes the attempted route, credentials, account, token role, and recommended action. It also showed that a deliberate vulnerability must be documented and contained. The weak signing key is useful only because the system is local, the admin data is fake, and the response path is visible. A second lesson is that configuration belongs to the system design. The Python code alone cannot produce a Wazuh dashboard alert. The agent localfile entry, TCP connection, manager rule file, indexer, dashboard, and active response configuration all have to agree. Testing each stage independently made troubleshooting more reliable. CHAPTER 6 CONCLUSION 6.1 Project Summary This project implemented a library management website and an application specific honeypot on one Windows host. Normal members use port 3000 to browse, borrow, return, and review books. A deliberately weak JWT signing secret supports an authorized role manipulation exercise. Suspicious administrator sessions are redirected to a decoy page on port 4000, where fake borrower files create high value detection events. A Windows Wazuh agent forwards those events to Docker based Wazuh services for rule matching, storage, investigation, and selected response. 6.2 Key Contributions A complete normal user workflow that makes the decoy part of a believable application rather than an isolated page. A contained JWT attack path that rejects algorithm none but demonstrates the risk of a weak symmetric signing key. A separate fake administration service with synthetic credential, loan, and fine files. Eight project specific Wazuh rules covering deception, authentication, access control, injection, scanning, and enumeration events. A selective active response that bans a forged personal account and revokes its stored credentials after bait interaction. A reproducible local architecture suitable for classroom demonstration and security analysis. 6.3 Project Limitations The prototype is intentionally not production ready. It uses HTTP on localhost, a weak JWT secret, known decoy credentials, and a simple password derivation scheme. Event thresholds are stored and calculated by a single Python process and are grouped mainly by source IP. The decoy may be recognized by a skilled attacker, especially if they compare service fingerprints or inspect the local environment. The system has not been load tested, independently penetration tested, or evaluated against public Internet traffic. Automatic banning changes an application account rather than blocking a network source. 6.4 Future Enhancements Move secrets and secure deployment values into environment configuration, and use a cryptographically random key outside the training mode. Replace the demonstration password derivation with a standard adaptive password hashing library such as Argon2id or bcrypt. Add TLS through a local reverse proxy and test secure, HttpOnly, and SameSite cookie behavior. Introduce correlation rules that combine scanner, path, login, and decoy events over a longer period without storing attempted passwords in clear text. Add a controlled fine payment workflow so overdue loans can be resolved without manual database changes. Use container volumes or deployment automation so custom Wazuh rules persist whenever manager containers are recreated. Evaluate decoy realism, false positives, detection latency, and resource use with a documented repeatable test set.

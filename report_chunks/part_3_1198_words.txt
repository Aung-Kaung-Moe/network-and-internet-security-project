CHAPTER 4 SYSTEM ARCHITECTURE AND IMPLEMENTATION 4.1 Overall Architecture Figure 4.1 Overall system architecture The browser first communicates with the real library service on port 3000. The Python backend serves the static HTML, CSS, and JavaScript files and exposes JSON API routes. It reads and updates the SQLite database in the same process. If a verified token contains an administrator role while the associated database account remains an ordinary user, the request is treated as a role manipulation signal and is redirected to the decoy service on port 4000. Security events are written to logs/wazuh-honeypot-alerts.jsonl. The Windows Wazuh agent monitors this file and sends new entries over TCP to the Wazuh manager container. The manager decodes the JSON and evaluates local rules. Matching alerts are stored by the indexer and displayed in the dashboard. For rule 100500, the manager can instruct the reporting Windows agent to run the ban script. 4.2 Attack and Deception Flow Figure 4.2 Intended JWT manipulation and honeypot flow The intended exercise begins with a valid member login. Because JWT payloads are encoded rather than encrypted, the role claim can be inspected. The attacker performs an offline dictionary search against the HS256 signature and discovers the deliberately weak key. After changing the role to admin and re-signing the token, the attacker replaces the library_jwt cookie. A request to the real site webadmin path is then redirected to the fake administration page. The decoy looks useful but does not expose a real administrator function. 4.3 Application Data Flow Registration inserts a user record with a generated identifier, the user role, and a derived password hash. Login compares the submitted value with the stored hash and issues a signed cookie after success. Borrowing creates a loan record, reduces copies_available, and calculates a due date fourteen days after the transaction. A normal return closes the loan and increases book availability. If the due date has passed, the interface displays 500 MMK for each overdue day and the return action is refused until the fine condition is addressed. The backend keeps operational and security data separate. Users, books, loans, tickets, bans, failed login attempts, and path probes are stored in SQLite. Events intended for Wazuh are appended to a JSONL file so the agent can consume them incrementally. SQLite is suitable for this local prototype because it is an in process, serverless database stored in a single file and requires no separate database service [15]. 4.4 Database Design Table | Purpose | Important fields users | Member identity and local role | id, username, full_name, role, password_hash books

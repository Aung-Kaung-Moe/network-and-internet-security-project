ABSTRACT This project develops a web based library honeypot that combines an ordinary borrowing service with a controlled decoy administration area. The real application runs on localhost port 3000 and supports book browsing, registration, login, borrowing, return processing, overdue fines, and personal loan records. Authentication uses a signed JSON Web Token stored in the library_jwt cookie. For the purpose of the security exercise, the HS256 signing secret is intentionally weak, while unsecured tokens using the none algorithm are rejected. A user who recovers the secret and changes the token role from user to admin is diverted to a fake administration page on port 4000. The page contains believable borrower credential, loan, and fine files. Access to these files produces structured JSON security events. A Windows Wazuh agent monitors the JSONL event file and sends new records to a Docker based Wazuh manager, where custom rules classify eight types of suspicious activity. The highest severity rule can call an active response script that bans the attacking account and revokes its stored credentials. The completed prototype demonstrates how a deliberate vulnerability can be contained inside a local teaching environment and connected to monitoring, investigation, and response. It also shows the limits of this design: the weak key and decoy credentials are suitable only for an isolated laboratory and must never be carried into a production system. JSON Web Token, or JWT, is a compact format for carrying claims such as a user identifier and role [1]. A signed token can protect those claims from modification, but that protection depends on correct algorithm validation and a signing key with enough entropy. RFC 8725 specifically warns that weak symmetric keys can be recovered through offline dictionary or brute force attacks after an attacker obtains a token [2]. This weakness is useful in a controlled security exercise because it creates a clear path from an ordinary user account to attempted privilege escalation. The project deliberately uses the short key book for HS256 signing. It still rejects the none algorithm, so the exercise distinguishes an implementation that performs signature verification from one that uses an unsafe key. Once an altered role claim is accepted, the application does not expose real administrative data. Instead, it moves the suspicious session into a decoy service where later actions can be observed. Honeypots are systems or resources designed to attract activity that has little or no legitimate reason to occur. Their value comes from the high signal of an interaction and the opportunity to record attacker behavior [3], [4]. In this project the decoy is application specific. It looks like a library administration page and offers files that an attacker may consider valuable, while the files contain synthetic records. Wazuh then provides centralized rule matching, alert storage, dashboard investigation, and active response. 1.2 Problem Statement A normal library application can record failed logins, but a basic log entry does not show how several suspicious actions relate to one session. The project therefore addresses three connected problems. First, it needs a believable application in which normal users can perform real work. Second, it needs a contained attack path that demonstrates JWT role manipulation without exposing genuine administrator information. Third, it needs a monitoring pipeline that turns application events into searchable alerts and can respond automatically to a high confidence deception event. The design must also control false positives. A forgotten password should not automatically ban a member, and a scanner signature by itself may not prove compromise. For that reason, most custom rules are review only. Automatic account banning is reserved for the stronger signal produced when a forged administrator session downloads a bait file. 1.3 Project Objectives The main objective is to design and implement a local web honeypot that detects JWT role manipulation and records subsequent attacker activity. The specific objectives are: Build a usable library website with public book browsing, registration, login, borrowing, returns, due dates, and overdue fine calculation. Use an HS256 JWT cookie for authentication and deliberately configure a weak signing key for an authorized laboratory exercise. Reject unsecured JWTs using the none algorithm while allowing the weak secret to demonstrate a different JWT failure mode. Redirect forged administrator sessions from the real website on port 3000 to a fake administration page on port 4000. Generate structured security events for bait downloads, login brute force, decoy login, IDOR probes, SQL injection probes, scanner user agents, and path enumeration. Integrate the application with a Windows Wazuh agent and Docker based Wazuh server components. Use a custom active response for the high confidence bait download event while leaving lower confidence events for analyst review. 1.4 Project Scope The project is a single host laboratory deployment. The real and decoy web services run on Windows, while the Wazuh manager, indexer, and dashboard run in Docker containers on the same machine. SQLite stores application data locally. Testing is limited to accounts, traffic, and files created for this project. The system is not exposed to the public Internet and does not collect data from unrelated users. The scope includes detection and response demonstrations rather than enterprise hardening.
